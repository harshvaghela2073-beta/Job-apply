# Deploying JOB·HUNT: frontend on Vercel, backend on Render

The backend (scanners, applying, emails) runs on Render as a Docker service with a persistent disk.
The frontend is a static site on Vercel that talks to it. An app password protects everything.

## Before you start

- **Render plan:** the backend needs a paid instance with about 2 GB of memory (Render's
  "Standard") and a persistent disk. The free plan can't work: it has no disk, so every restart
  erases the database and logins, and it sleeps when idle, which stops the scan schedule. Check
  Render's current prices.
- **Account risk:** the server's address is a data-centre address in Singapore. LinkedIn and Naukri
  may ask for security checks or restrict the account when it is used from there. If that happens,
  pause the platform in the scanner panel and run the backend on a home machine instead.
- **Run one copy only:** once the server scans, stop the backend on your Mac (or set
  `SCAN_ENABLED=false` in `backend/.env`). Two copies would apply and email twice.
- The repository must be on GitHub (private is fine). `.env`, the database and the browser logins are
  gitignored and never uploaded with the code; you send them to the server in step 3.

## 1. Backend on Render

1. In Render: **New → Blueprint**, pick the repository. Render reads `render.yaml` at the repo root:
   one Docker web service `jobhunt-backend` (Standard plan, Singapore, one instance) with a 2 GB disk
   at `/data`.
2. Fill in the values Render asks for:

   | Variable | Value |
   |---|---|
   | `APP_PASSWORD` | A long password for the app (you type it on the login screen). |
   | `CORS_ORIGINS` | Your Vercel address, e.g. `https://jobhunt.vercel.app` (set it after step 2 if you don't know it yet). Several: comma-separated. |
   | `SMTP_USER` | Your Gmail address. |
   | `SMTP_APP_PASSWORD` | The Gmail app password from `backend/.env`. |
   | `SMTP_FROM_NAME` | Your name, as on the emails. |

   `AUTH_SECRET` is generated by Render. The Dockerfile already sets Chromium, Asia/Kolkata time and
   every file path on the disk.
3. Deploy. When it is live, open `https://<your-service>.onrender.com/api/health`: it shows
   `{"status":"ok"}`.

## 2. Frontend on Vercel

1. In Vercel: **Add New → Project**, import the repository, and set **Root Directory** to
   `frontend` (Vercel detects Vite; `frontend/vercel.json` sends every page to the app).
2. Add the environment variable `VITE_API_BASE_URL` = `https://<your-service>.onrender.com` (no
   trailing slash). It is built into the app, so change it → redeploy.
3. Deploy, then put the Vercel address into `CORS_ORIGINS` on Render (Render redeploys by itself).

## 3. Move your data to the server

On your Mac, in `backend/`, with the server live. Each command asks for the app password (or set
`JOB_APPLY_PASSWORD` for the session):

```bash
# Your profile, templates, job history and settings (a consistent copy of the local database)
.venv/bin/python -m app.tools.push --server https://<your-service>.onrender.com database

# Your resume (attached to the hiring-post emails)
.venv/bin/python -m app.tools.push --server https://<your-service>.onrender.com resume

# Your LinkedIn and Naukri logins, read from your Chrome (macOS asks for "Chrome Safe Storage")
.venv/bin/python -m app.tools.push --server https://<your-service>.onrender.com login all
```

Each prints a short result: the counts that arrived, or each platform's connection status.

## 4. Check it

Open the Vercel address, log in with the app password, and on the Dashboard open **Scanner**: both
platforms should show your name. Press **Run now** on one platform and watch the result.

## Day to day

- **A platform shows "disconnected"** (its login expired, or LinkedIn asked for a check): open it in
  your Mac's Chrome, log in or finish the check there, then run
  `push ... login linkedin` (or `naukri`) again.
- **Logs and screenshots:** Render dashboard → Logs. Failure screenshots are on the disk in
  `/data/diagnostics` (Render dashboard → Shell).
- **New code:** push to GitHub; Render rebuilds the backend when `backend/` changes, Vercel the
  frontend. Your data stays on the disk.
- **Back to local:** stop or suspend the Render service, start the backend on your Mac again. The
  server's data stays on its disk; your local database is as you left it.

## If something is wrong

| You see | Check |
|---|---|
| "Can't reach the backend" | `VITE_API_BASE_URL` on Vercel (then redeploy), and that the Render service is live. |
| The login screen keeps coming back | `CORS_ORIGINS` on Render must match the Vercel address exactly (https, no trailing slash). |
| "Too many attempts" | Five wrong passwords lock logins from that address for 15 minutes. |
| Scans fail with browser errors | Render logs; the instance may be short of memory (pause one platform or use a larger plan). |
